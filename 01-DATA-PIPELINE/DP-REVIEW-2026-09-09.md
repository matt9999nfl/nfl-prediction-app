## 0. Headline

The six changes are, with one exception, sound. The principle they claim — *the
current season warns, completed seasons still error* — is upheld in five of them,
and the historical guarantees are almost entirely intact. The exception is
`ingest_pbp.py`, and it is the first of the two findings below.

Neither of the two findings is a change PROJECT-LEAD made. Both are things the
changes now sit inside.

### Finding 1 — a silent-failure loop that survives all four INC-002 fixes

Three facts, each individually defensible, compose into a path where a season of
history leaves the warehouse and every signal stays green.

1. **`run_pipeline.run_ingest_pbp` drops the whole table before it ingests
   anything.** `drop_table_if_exists(client, "raw_nflfastr.pbp")` runs once, then
   the loop over 2015–2026 begins. Five such call sites across the run: schedules,
   pbp, rosters, `curated.games`, `curated.plays`.
2. **`ingest_pbp`'s new `EMPTY` branch is not season-gated.** `if len(df) == 0`
   applies to 2015 exactly as it applies to 2026. An empty fetch for a *completed*
   season is now reported `EMPTY`, skipped, and tolerated — where previously it
   reached `validate_pbp`, failed the 40,000-row floor, and stopped the run. This
   is the only place in `42336b6` where a historical guarantee was weakened, and
   the only one of the four fixes that does not ask which season it is looking at.
3. **`validate_and_report` can only fail a check about data it can see.** Every
   per-season check is generated by iterating a `GROUP BY season` result. A season
   with no rows produces no group, therefore no label, therefore no check,
   therefore no failure.

Run them in order: table dropped → season fetches empty → skipped → season now
absent from production → no label generated for it → **ALL CHECKS PASSED**, exit 0,
no alert. A decade of play-by-play can leave without one red character anywhere in
the output.

**Probability is low.** `nfl_data_py.import_pbp_data` raises on a missing release
asset rather than returning an empty frame; this needs a source that serves a
valid-but-empty parquet. **Impact is total and silent.** That combination is the
exact shape of the 40,000-row floor — the standing proof, in this folder, that this
codebase produces failures which never announce themselves — and it is why the
40,000-row floor being fixed did not fix the class.

**Cost to close: one clause**, `if len(df) == 0 and season >= current_season():`.
Below it, an empty completed season falls through to `validate_pbp` and errors as
before. **This does not re-break the 2026 ingest** — 2026 still takes the `EMPTY`
path. Not applied; see §7.

### 1.1 `scripts/run_pipeline.py` — closing-line gate to warning — *correct-but-narrow*

**What it no longer catches on history:** nothing, in the end — but detection moved
five steps later. The gate was on a single aggregate null rate across all seasons.
Downgrading it removes the only pre-write signal that historical closing-line
coverage has collapsed. The per-season backstop survives: `spread_null_rate_{s}`
in `validate_and_report` still errors at ≤5% for every completed season. So a
2015–2019 `spread_line` regression is still caught — at step 7, after
`curated.games` has been dropped and rebuilt from the bad source, rather than at
step 2 before anything was written.

**Narrowness.** The right fix was to exclude the in-progress season from the
aggregate and keep the error, preserving a gate *as a gate*. What landed removes
the gate for every season to accommodate one.

Also: the warning text asserts that nulls "will backfill as the season progresses."
That is a prediction stated to an operator as fact. It is probably true; it is
verified nowhere.

### 1.2 `adapters/nflfastr.py` — `current_season()`, 40k floor advisory — *correct-but-narrow*

**What it no longer catches on history:** nothing. Completed seasons keep the hard
40,000 floor; the column-presence checks still apply to every season.
`season >= current_season()` also covers future seasons, which is the right
default. This one does exactly what it says.

**Narrowness — the sharpest of the six.** The in-progress season now has **no
row-count protection of any kind.** Any count below 40,000 is a warning labelled
"expected for an in-progress season". In week 10 a 300-row fetch is not expected;
it is a truncated source. Because the table is dropped before the loop, that 300
rows becomes the whole of 2026 in production and the run exits 0.

A floor is the wrong instrument for a growing season. A **monotonicity** check is
the right one — this season's count must not be materially below what the table
already held. That is a new check rather than a loosened one, and it is not a
pre-weekend change.

**Also:** `current_season()` was introduced as the shared definition and **nothing
imports it.** Eight other modules each carry a byte-identical copy of
`datetime.now().year - (1 if datetime.now().month < 7 else 0)` —
`audit_closing_lines`, `build_curated_games`, `build_curated_plays`, `ingest_pbp`,
`ingest_rosters`, `ingest_schedules`, `reset_and_run`, `run_pipeline`,
`validate_and_report`. The choke point was written but not taken (DP-R-09).

### 1.3 `scripts/ingest_pbp.py` — zero plays returns `EMPTY` — ***wrong***

The substance is Finding 1 in §0. Summarised here for the table's sake: the
`EMPTY` branch is not season-gated, it is the only place in the commit where a
historical guarantee was weakened, and its blast radius comes from the drop that

**Second, separate defect in the same file.** `main()` line 123 still reads

path documented in this file's own docstring is broken for the current season

## 3. The six questions

### Q1 — `current_season()` uses month < 7. Correct? Does anything run Jan–Jun where it matters?

**The cutover is correct.** A January playoff game belongs to the previous season's
label, and `year - (1 if month < 7 else 0)` gives exactly that: January 2027 → 2026.

**Jan–Jun is the safe window, not the risky one.** In those months `SEASONS` ends
at a season that has finished, so completed-season thresholds are correct and the
advisory path is correctly inactive.

**The risky boundary is 1 July.** On the first run on or after 1 July 2027,
`CURRENT_SEASON` increments to a season with no games played:

| Step | 2027 in July 2027 | Outcome |
|---|---|---|
| 1 schedules | published in May, ~272 rows | passes |
| 3 pbp | 0 rows → `EMPTY` | tolerated |
| 4 **rosters** | `import_weekly_rosters([2027])` | **exposure — below** |
| 5/6 curated | 0 rows | `EMPTY` tolerated (plays) / OK (games) |
| 7 validate | 2027 labels → advisory | correct |

Step 4 is the exposure. `validate_rosters` checks only that five columns exist. An
empty frame from `nfl_data_py` may arrive with no columns at all, in which case all
five are "missing", status is `VALIDATION_FAILED`, and `_print_summary` exits 1.
**The pipeline would then die at step 4 on every run until roster data publishes.**
Gate 2's shape exactly, in a check nobody has looked at, ten months out.

**Minor, real:** `datetime.now()` is local time. In the container that is UTC; on
Matt's machine it is UTC+12. For twelve hours around each 1 July, laptop and job
compute different `CURRENT_SEASON` values. Harmless today; confusing the day
someone diffs local output against job output.

### Q2 — `validate_rosters` has no row-count check. Should it?

**Yes, and the situation is worse than the question assumes: there is no backstop
either.** `validate_and_report` computes the roster row count and discards the
result without checking it (§1.6). Rosters have **zero enforced row-count
protection at any layer** — not in the adapter, not in the report.

The two failure modes are also inverted from what you would want. A roster fetch
returning *fewer rows than it should* passes silently. One returning *nothing at
all* fails loudly — but as a missing-column error, which misdescribes the problem
to whoever reads the log.

**Recommended:** `n > 500` per season as an error for completed seasons, advisory
for the in-progress one, in **both** places — the adapter, and the `check()` call
the report is already one line away from making.

### Q3 — `validate_schedules` keeps a hard 256 floor. Reliable, or luck?

Neither, exactly. It is an **unstated dependency**: the schedule publishes in May,
the season label flips in July, so there is roughly seven weeks of margin. Not
luck — but nothing asserts it and nobody wrote it down.

**The floor is separately wrong on its own terms.** 256 is the 16-game era
(32 × 16 ÷ 2). The regular season has been **272 games since 2021** (32 × 17 ÷ 2).
The floor sits 16 games *below* the actual minimum, so a modern season could lose
an entire week and still pass.

`expected_max = 290` is tight too: 272 REG + 13 playoff = 285, five games of
headroom. An 18-game season (32 × 18 ÷ 2 = 288, + 13 = 301) breaks it outright.

**Recommended:** 272 for seasons ≥ 2021, 256 before. Not a weekend risk.

### Q4 — Is `EMPTY` handled consistently, or are there more call sites with the `build_curated_games` bug?

**No, and yes.** Six call sites, split three and three:

| Tolerates `EMPTY` | Does not |
|---|---|
| `run_pipeline.py:240` | `ingest_pbp.py:123` |
| `build_curated_plays.py:237` | `ingest_rosters.py:117` |
| `build_curated_games.py:219` | `ingest_schedules.py:120` |

Of the three that do not tolerate it, **only `ingest_pbp.py` can currently receive
an `EMPTY` — and it is the file that introduced the status** (DP-R-05).
`ingest_rosters` and `ingest_schedules` never emit it today, so they are latent:
whoever adds an empty path to either inherits the `build_curated_games` bug for
free.

And of the three that do tolerate it, **`build_curated_games` tolerates a status
its own module cannot produce** (§1.4).

The fix landed in the one place it does nothing and was omitted from the one place
it was reachable. Two of the remaining three are traps for the next author.

**Structural recommendation**, per the methodology's preference for structure over
instruction: these are bare string literals compared ad hoc across six files. A
small enum with `is_failure()` on it makes the entire class impossible rather than
prohibited. After the weekend.

### Q5a — Can a label match or miss for the wrong reason?

Yes, in both directions — but the category error matters more than either case.

At every call site the season is **already an integer in scope**:

```python
all_pass &= check(ok, f"pbp_{s}_row_count", check_results)
```

`s` is an `int`. The label formats it into a display string; `is_in_progress_season`
then string-matches it back out. The value was never unavailable — it was discarded
and then reconstructed unreliably. That is *never compare system output as a
string* in its purest form, and the reconstruction fails silently in the direction
that disables checks.

- **Miss** (fails hard when it should be advisory) — any per-season label where the
  token is not `_`-delimited or terminal. `pbp_2026_rows_v2` matches;
  `pbp2026rows` does not; `rows_2026a` does not. Every current label conforms, so
  this is latent.
- **Match** (goes advisory when it should be enforced) — the dangerous direction.
  Any label containing `_2026_` or ending `_2026` for a non-season reason. Note
  that `cover_rate_{bucket}` labels are built from a SQL `CASE` expression
  (`home_fav_3-10`, `home_dog_3-10`). Change a bucket boundary to a year-like
  number and you silently disable the semantic cover-rate check — the check INC-001
  exists because of.
- **Third, subtler:** the function is applied to *every* label, including
  `qb_hit_zero_nulls`, `no_duplicate_game_ids` and `overall_cover_rate_46_to_54`.
  Those are safe only because none happens to contain a four-digit year. That is a
  coincidence of naming, not a property of the design.

**Fix:** `check(condition, label, results, season=None)`, compared as
`season == CURRENT_SEASON`. Mechanical, no behaviour change for any existing label.
It touches the file that runs on Friday, so: after (DP-R-04).

### Q5b — What happens to every per-season check on 1 January?

**Nothing. The premise is wrong, and that is worth more than the answer.**

`CURRENT_SEASON = datetime.now().year - (1 if datetime.now().month < 7 else 0)`
returns **2026 on 31 December 2026 and 2026 on 1 January 2027.** The constant does
not roll over on 1 January. The 2026 labels keep matching until 1 July 2027.

The scenario as posed — a container that starts in December and is alive in January
— resolves the same way. `CURRENT_SEASON` is module-level, evaluated at import, so
a process that imported in December holds December's value, which here is the same
value January would produce. No drift in either direction. Cloud Run job executions
are single-shot processes in any case; none survives to New Year.

On 1 January the report behaves exactly as it did on 31 December. 2026 checks stay
advisory, correctly — 2026 is still being played until February. On 1 July 2027
they flip to fully enforced, also correctly. The design handles the year boundary
properly, and the only calendar exposure is the July one in Q1.

**But the report does go quiet — just not on a date.** It goes quiet whenever a
season stops being present in the table, because every per-season check is
generated from `GROUP BY season` over the rows that exist. An absent season
produces no label, no check, and no failure. That is a year-round property, it is
the third link in Finding 1, and it is the answer that outranks the one the
question asked for: **the report can only fail a check about data it can see.**

## 6. Conclusion — the disease, not the symptom

The four INC-002 gates, the six HC-S6 defects, and both findings in this review are
one failure repeated: **the thing that should have reported a problem was itself
silent.** Not wrong answers — absent ones. A 40,000-row floor that would have
failed every Sunday until December without announcing itself. A row check computed
and thrown away. A validator that iterates only the seasons still present. An alert
policy structurally incapable of firing.

The clearest single artefact of it is one line, in the production entrypoint, since
the initial commit:

```python
# Note: Confirm with DATA-PIPELINE that --start-at 1 is the correct invocation
```

Someone wrote a question to another agent, in a code comment, and shipped it. The
question was never asked, never routed, never answered, and never blocked anything.
It sat in the file that every scheduled run executes, being read by nobody, while
the thing it was uncertain about ran three times a week.

**The timeout is the symptom. That comment is the disease.** A question addressed to
a named owner is a handoff; a handoff that lives in a comment has no delivery
mechanism and no acknowledgement, so it silently becomes a decision by default. It
is the same structure as the alert with no `trigger` block: present, correct-looking,
and incapable of doing its job.

The structural lesson, in this project's own terms: **an uncertainty that cannot
fail is not recorded, it is discarded.** A question to another agent belongs in that
agent's `instructions.md` or in the escalation file, where it blocks something. In
a comment it is indistinguishable from a decision.

### 7.2 Spec — gameday restricted to the current season, written per-partition (DEFERRED)

Not implemented. Deferred until after the first live weekend, per PROJECT-LEAD
2026-09-09.

**The step-selection axis in the first draft of this section was wrong.** The
correction is recorded rather than quietly replaced, because the reason is more
useful than the answer.

**DP-REVIEW-Q1, answered 2026-09-09 — step 6 cannot be skipped.** `curated.plays`
is read by the live API, not only by MODELING. Verified in source:

| Reader | What it uses `curated.plays` for |
|---|---|
| `app/queries/games.py:185` | play count per game |
| `app/queries/games.py:219` | per-team aggregates for game detail |
| `app/queries/teams.py:93` | EPA series |
| `app/routers/teams.py` | EPA charts |

`app/routers/games.py:117` is explicitly best-effort — *"Play count (best-effort;
don't fail the request if curated.plays is empty)"* — and wraps both the play count
and the team stats in `try/except`. So skipping step 6 does not break the site; it
makes game detail and team stats **up to seven days stale during the season**,
degrading silently rather than erroring. Not acceptable in September.

MODELING reads `curated.plays` only in on-demand backtests and has no freshness
requirement between scheduled runs. That half of the question was a non-issue.

**And the dependency makes step selection unusable regardless of the answer.**
Step 6 builds `curated.plays` **from** `raw_nflfastr.pbp`, which step 3 populates.
Step 6 without step 3 rebuilds `curated.plays` from stale raw data and updates
nothing. Any subset containing 6 must contain 3; any gameday run containing 3 is a
full PBP refetch, which is the cost the mode existed to avoid. So `{1, 5}` was the
wrong shape and `--only` was the wrong instrument — the steps are not independent
and cannot be selected as though they were.

**The axis is season scope, not step selection.** A gameday run should execute the
same seven steps, each restricted to the current season, each writing to its season
partition instead of dropping the table.

**This subsumes DP-R-12 rather than working around it.** Per-partition writes remove
the availability window instead of shortening it: `curated.games` is never absent,
so the games API never sees an empty table. `curated.plays` is already partitioned
on `season` — `app/queries/teams.py:19` documents the API relying on that — and
both the ingest and curated builders already load to `{table}${season}`. **The five
`drop_table_if_exists` calls in `run_pipeline.py` are the only reason a run is
destructive at all.**

**Shape of the change:**

- `SEASONS` for a gameday run becomes `[current_season()]` rather than `range(2015, …)`
- the five `drop_table_if_exists` calls go; `ensure_table_with_schema` stays
- `WRITE_TRUNCATE` on `{table}${season}` already scopes each write to its partition,
  so no write logic changes

**Must be resolved before implementation:**

1. **Why the drop exists.** `drop_table_if_exists`'s own docstring says it is there
   to let BigQuery propagate a clean schema after a type change, and that without
   the 10s sleep a retry hits the stale schema and fails on the first partition.
   Removing it has to be verified against schema evolution — a season whose vendor
   columns change shape mid-season. **This is the reason it is not a one-line
   change**, and it should be treated as the load-bearing question, not a formality.
2. **Whether `validate_and_report` still passes on a current-season-only run.** It
   iterates every season present in the table, and the table keeps its history under
   this design, so it should. That is the check to run, not to assume — and it is
   the same assumption Finding 1 is about.
3. **Whether the Tuesday full run remains the mechanism for historical correction.**
   If gameday no longer touches completed seasons, the weekly full run becomes the
   only path by which a historical error is ever repaired.

**Acceptance:** a gameday run completes well inside 1800s; the games API returns a
non-empty result at every point during it; rows for completed seasons in
`raw_nflfastr.pbp` are unchanged by a gameday run; a full run still rebuilds
everything.

## 9. DP-R-13 — `:latest` is a mutable tag on both pipeline jobs

**Filed 2026-09-09 by PROJECT-LEAD. Owner: DEVOPS. This outranks DP-R-01.**

Both `nfl-pipeline-full` and `nfl-pipeline-gameday` reference
`gcr.io/nfl-model-471509/nfl-data-pipeline:**latest**`. Neither job spec records a
digest. So the job definition does not say what code the job runs — it says where
to go and ask, at the moment it starts.

**This is not theoretical, and 2026-09-08 is the proof.** That day the 07:00
gameday run and the 11:00 full run executed **different images from the same tag**,
because a build landed at 09:23 between them. Nothing in either job spec, and
nothing in either execution record, says which. The two runs are indistinguishable
in configuration and were not running the same software.

**The digest history is INC-002 with a receipt.** Builds jump from 2026-05-08
straight to 2026-09-07: four months of nothing. That gap is the stale image the
incident took a week to diagnose, sitting in the registry the whole time, legible
to anyone who thought to look — and nobody could have known to look, because the
job spec pointed at a tag rather than a digest and therefore looked identical
before and after.

**It is the pipeline-side twin of `/health` reporting `commit:"unknown"`.** Both
are the same omission: a running artifact that cannot say what it is. Residual
item 4 in INC-002 covers the API side; this is the same defect on the jobs, and it
is the one that mattered in the incident.

**Fix:** pin the digest, or tag by commit SHA, on both job specs. Owner DEVOPS.

**Why it outranks everything else in §4.** Every other finding in this review is a
statement about code. This one is about whether a statement about code can be
connected to what is running at all. §8.1 above took a conversation, a build
timestamp and an eleven-hour arithmetic comparison to establish something a pinned
digest would have made a lookup — and §8.1 is the precondition the whole review
rests on. **A review that cannot cheaply identify its own subject is the failure
mode one level above the ones catalogued here.**

It also closes the loop on §6. The four INC-002 gates, both findings in §0, and
this one are the same disease: the mechanism that should have reported a problem
was silent. A mutable tag does not report which image ran. It answers, correctly
and uselessly, `latest`.
