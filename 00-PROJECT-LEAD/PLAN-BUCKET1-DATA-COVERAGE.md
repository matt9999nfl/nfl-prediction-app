## The finding this plan is built on

Picks are generated by the Tue 14:00 UTC production refresh, for games that kick off
the following Sunday. That is roughly 4.5 days before kickoff, and before that week's
first injury report exists. **The model currently decides as early as possible.**

Adding late prediction runs today would change nothing. Of the 23 base features
(`features/families.py`), not one changes value between Tuesday and Sunday — they are
all season-to-date play-by-play aggregates plus static game context. A T-90min re-run
would produce a byte-identical feature vector.

**So the order is forced: time-varying features first (B1-3), late runs second (B1-5).**
Building the scheduling before anything varies in time is the expensive way to do nothing.

## B1-3 — Timestamped observation layer, and the first time-varying features

**Outcome:** at least one feature the model reads has a different value on Sunday
morning than it had on Tuesday, and the platform can reconstruct what any feature's
value was at any past timestamp.

`raw_lines.line_snapshots` is already the right shape: append-only, one row per observed
change, nothing updated or deleted. This stage generalises that pattern rather than
inventing a second one. Every row in the new sources needs an observation timestamp, not
just a season/week key, because injury reports, depth charts, weather forecasts and lines
all arrive at different points in the same week.

The first three time-varying features, in order of how cleanly they backtest:

1. **Injury report status and practice participation.** *Gate answered 2026-09-18,
   against `ol_injuries_2015_2025.parquet` (see "Point-in-time verification" below).*
   Exactly one row per (season, week, team, player), 10,937 rows, with a `date_modified`
   timestamp that is Friday for 79% of rows. So this is the week's **final** injury report,
   timestamped — it backtests honestly, and it is the best feature available in bucket 1.
   It is not an intra-week progression: there is one `practice_status` per player-week, so
   the DNP/Limited/Full pattern across Wed-Thu-Fri is **not** recoverable from the archive
   and only forward capture will ever get it.
   Three handling requirements, all mandatory: `date_modified` is null for 9.9% of rows,
   which cannot be placed in time and must be excluded from any point-in-time feature; 32
   rows are modified on a Sunday or Monday and are a live leakage risk; and `report_status`
   uses the **literal string** `"None"` for 5,476 rows rather than NULL, so an `IS NULL`
   check silently misses half the data (the same class of defect as INC-001).
2. **Projected starters from weekly depth charts.** *Gate answered 2026-09-18, and the
   answer is worse.* `ol_depth_charts_2015_2025.parquet` has **no 2025 rows at all**
   despite the filename and the staging README both claiming 2015-2025 — coverage stops
   at 2024, which means no data for the current season. Its `dt` timestamp column is null
   for every pre-2025 row, so there is no observation time and no point-in-time evidence.
   And it is not unique per player-week: 6,679 keys have 2 rows and some have up to 8,
   because a player can be listed at more than one `depth_position`. Treat this source as
   unusable for a live feature until it is refetched and the 2025 gap explained. This is
   exactly the silent-absence failure DP rule 5 warns about.
3. **Weather as a forecast at time t rather than as observed.** Note the overlap:
   `PROMPT-PICK-EXPLANATIONS-AND-EDGE-LAB.md` Stage 3.5 already covers the live defect
   where training uses actual game-day weather while predictions get median temperature
   and zero wind. Do not build that twice. If Stage 3.5 has landed, this stage extends it
   to a stored forecast history; if it has not, this stage waits on it.

**Needs Matt, not a worker session:** a timestamped odds source. nflverse gives one
weekly `spread_line` field, so intra-week line movement — the market telling you what it
learned from the injury reports — needs an external feed with its own account and key.
The Odds API is the cheap option; Betfair's exchange gives traded liquidity rather than a
posted number. No code stage should assume this exists until Matt has decided.

**Kill-switch:** stop if the injuries or depth-chart verification shows final-state data
and the stage would proceed anyway; if a time-varying feature would reuse an existing
feature column name; or if any feature's value at prediction time could be influenced by
data timestamped after the scheduled kickoff.

**Acceptance:** a stated, evidenced answer to the point-in-time question for injuries and
depth charts · every row in the new observation tables carries an observation timestamp ·
a documented query that returns a feature's value as at an arbitrary past timestamp · at
least one feature whose value provably differs between a Tuesday and a Sunday snapshot
for the same game · a no-lookahead test in the same shape as the existing `ol_metrics.py`
guarantee (features for week W use only data observed before that game's kickoff).

## B1-5 — Multiple prediction runs per game, graded by decision time

**Outcome:** the platform can answer "what would we have picked at T-72h, T-24h, T-3h,
T-90min" and grade each separately, so the value of waiting is measured rather than assumed.

Do not start this before B1-3 has landed at least one time-varying feature. Until then
every decision time produces the same vector and the whole stage measures nothing.

The question this exists to answer is not "should we use injury data" but "how much does
each hour of waiting buy, and where does the curve flatten". The expected shape is lumpy:
near-nothing Monday to Wednesday, a step at Friday's game-status designations, a second
step at the T-90min inactives. If that is the shape, the answer is two well-timed batch
runs, not a streaming architecture — which is a much cheaper platform, and only
measurement will say so.

Interacts with two standing rules: never rewrite a pick for a game that has kicked off,
and don't generate predictions between a week's first kickoff and the end of that week's
games. Multiple runs per game must be additive rows, not overwrites, and the served pick
needs a defined rule for which run it shows.

**Acceptance:** predictions for one week stored at three or more distinct decision times,
each with its feature vector and observation timestamps · each graded separately · a
report of log loss by decision time · the served pick unchanged in behaviour unless Matt
has agreed otherwise.

## Point-in-time verification (2026-09-18)

Run from Cowork against the staged parquet files, before the B1-3 stage was written into a
prompt, because the answer determines the design. Method: row-count by key, `date_modified`
day-of-week distribution, value counts and per-season coverage. Recorded here so the B1-3
session does not repeat it and does not discover the depth-chart gap late.

| Question | Injuries | Depth charts |
|---|---|---|
| Grain | 1 row per player-week (10,937) | not unique — up to 8 rows per player-week |
| Observation timestamp | `date_modified`, 79% Friday | `dt` null for every pre-2025 row |
| Season coverage | 2015-2025, all seasons present | **2015-2024 only — no 2025** |
| Backtests honestly? | yes, as a final weekly report | no |
| Intra-week progression? | no — one `practice_status` per week | no |

The practical consequence for B1-5: from the archive, the injury feature changes value
exactly once per week, on Friday. Together with inactives at T-90min (B1-4, no archive
exists), that gives the decision-time curve two steps, not a continuum — which is the
two-well-timed-runs shape, and an argument against building streaming infrastructure.
