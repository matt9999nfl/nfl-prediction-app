## 2. The sprint, assessed

Ten defects in three days, every one of them real, and the two most consequential
were invisible before this sprint started:

- **The deploy workflow had never shifted traffic.** Every deploy that ever
  landed came through the ad-hoc Cloud Build path, which never passed
  `GIT_COMMIT`. That single fact explains `/health` reporting `unknown`, and it
  explains why *"which code is actually running?"* took a week during INC-002.
  Fixing it retired an entire class of future confusion.
- **Predictions were not reproducible across machines.** `n_jobs=-1` meant
  XGBoost's histogram builder summed gradients in thread-completion order, so
  core count changed the answer. Largest local↔cloud delta went from 4.2e-2 to
  2.8e-8; two of sixteen picks had been flipping. **Verified in
  `models/ol_xgb.py` and `models/xgb_v2.py` — `n_jobs=1`, `tree_method="hist"`.**

The reasoning quality on the second one deserves specific credit. The
discriminating evidence — *two cloud runs byte-identical to each other, both
differing from local* — is a hardware signature, and reading it correctly meant
abandoning a plausible and much more visible pandas-version hypothesis. The
sprint summary is candid that the wrong hypothesis was reached for first. That
candour is worth more than the fix.

### 2.1 The load-bearing claim, independently checked

The sprint summary asked a reviewer to scrutinise the placeholder-plays technique
in `predict_upcoming.py`. **I traced it through both feature builders and it
holds.**

The argument as given — *the cumulative step is `cum - current_week`, so the
placeholder's own counts subtract back out* — is correct, and correct for a
slightly wider reason than stated:

- `features/ol_metrics.py:281` — `df[f"{col}_cum"] = cum - df[col]`. For target
  week *W*, the window is weeks 1..*W*−1. The placeholder's own row is removed by
  construction, not by luck.
- `features/comprehensive.py:271` — the same pattern, applied to all fourteen v2
  count columns. **This is the one the summary did not claim and the one that
  mattered to check**: had `compute_additional_team_features` used an
  `expanding()` or unshifted rolling mean, the placeholder would have polluted
  silently. It does not.
- `comprehensive.py:314` — `rolling_3wk_epa_trend` uses
  `.shift(1).rolling(3)`, so the placeholder week is shifted out before the
  window opens.
- `qb_cpoe` is safe by a different route: the placeholder sets `cpoe = np.nan`
  and `_per_game_qb_off` drops null-cpoe rows, so it never enters that
  numerator or denominator.
- The week-1 cold-start path is unpolluted. The placeholder creates a
  (team, 2026, 1) row; season averages are keyed `season + 1`, so it could only
  reach a 2027 week-1 cold start — and by then 2026 is complete and the
  placeholder has moved to 2027. **It self-corrects.** I went looking for a
  latent trap here and there isn't one.

**Verdict: sound. Use it.** The design decision to append placeholder rows rather
than fork the feature builders is the right one — it keeps one tested code path
instead of two, and the argument for why it is inert is checkable in four lines
of source.

### 2.2 A gap the sprint did not name

`predict_upcoming.py` **trains a fresh model on every run**, and the training set
grows each week. Week 1's model saw 2,822 games (2015–2025). Week 5's will see
those plus 2026 weeks 1–4. No model artifact is persisted. All of these different
models are written under one stable `experiment_id`
(`00000000-0000-4000-8000-00000000f0re`) with `run_count + 1`.

That is a defensible design for a rolling in-season model. But it means that when
a team's probability moves between weeks, **the platform cannot say whether the
team changed or the model did** — and it currently reports both under a single
experiment identity.

For a project whose entire purpose is measuring things honestly, that is a
capability gap worth naming (charter §5). It is not urgent and it is not a
correctness bug. It belongs in the queue, not this week.

## 3. New findings

Six things I found that are not in the sprint summary. Ordered by consequence.

### N-1 — The retired 54% gate is still live in code, and on the dashboard

**This is the mechanical answer to "why does the old framing keep coming back?"**

ADR-006 retired the project-level ≥54% ATS gate on 2026-05-03.
`predict_upcoming.py` writes `"success_threshold": 0.54` into
`experiment_configs.evaluation` (`build_config_payload`) and into
`backtest_runs.success_criteria` (`build_run_row`) on **every single production
run**, and `gate_passed: false` — measured against that — is what drives the
honest-evaluation banner users see.

So the app currently re-asserts a retired project-level gate into the database
every Tuesday, and renders the failure of it to every visitor.

The framing problem is not stale prose. **The old premise is encoded in the
running system.** Cleaning up the documents without cleaning this up will not
hold, because the next cold session will read the database and the UI and
correctly conclude the project has a 54% gate. Full inventory in
`PROJECT-CHARTER.md` appendix.

*Not urgent — it is cosmetic to correctness and the banner is currently telling
users something true (this model is unvalidated). But it should be fixed before
it teaches another session the wrong thing.*

### N-2 — `require_api_key` fails open

`03-BACKEND-API/app/dependencies.py:62`:

```python
if not settings.owner_api_key:
    # Dev mode: key not configured → open (no-op)
    return
```

If `OWNER_API_KEY` is absent, every write endpoint is unauthenticated — including
`POST /api/v1/predictions/refresh`, `POST /api/v1/experiments`, and the dataset
upload path. The service is public (`roles/run.invoker` → `allUsers`,
`cloud_run.tf:79`). There is no startup assertion that the key is present in
production.

The convenience is real and the intent is clear, but the same code runs in both
environments and the failure is silent in the dangerous direction. **Fail closed:
require the key unless an explicit `DEV_MODE` flag is set, and assert at startup.**

### N-3 — Two systems own the Cloud Run service spec

`05-DEVOPS/infra/terraform/cloud_run.tf` declares the container env, both
secret-backed env vars, concurrency, timeout and scaling. `.github/workflows/api-deploy.yml`
re-declares an overlapping subset on **every push**:

```
--max-instances 3 --memory 512Mi --cpu 1 --timeout 60 --concurrency 80 \
--set-env-vars=BIGQUERY_PROJECT=...
```

Terraform also declares `traffic { latest_revision = true }` while CI deploys
`--no-traffic --tag candidate` and then shifts traffic explicitly. These two
descriptions of the same resource cannot both be current.

Note `--set-env-vars` rather than `--update-env-vars`: the deploy asserts
ownership of the service's entire literal environment on every push, while
Terraform asserts it too.

**I am flagging this as "go and look", not as a confirmed break** — the live
service is healthy right now, and I did not run `terraform plan` against it.
Running that plan is the cheap way to find out what has drifted, and it is
exactly the kind of check that is worth doing *before* someone runs
`terraform apply` for an unrelated reason and reverts the service to a state CI
has been overriding for months. Combined with N-2, an env-var mishap here is
silently a security change.

### N-4 — Traffic shifts to the latest *created* revision, not the tested one

`api-deploy.yml:134` — `--to-revisions=LATEST=100`. The revision that was
smoke-tested is already captured in `steps.revision.outputs.revision` and then
not used. Two overlapping deploys, or any manual `gcloud run deploy` during a
workflow run, would move traffic to code that was never tested.

The `Verify traffic shift` step catches this *after* the shift by asserting the
commit SHA, which is a good guard and the reason this is a small finding rather
than a large one. But pinning the revision name is a one-line change that makes
the smoke test actually load-bearing instead of advisory.

### N-5 — The frontend generates its API types from the live API at build time

`frontend-deploy.yml:57` — `npm run types:generate -- --url <live api url>`.

The frontend's TypeScript contract is therefore *whatever production is currently
serving*, not what the repo says. If the frontend deploys before the API, it
builds and typechecks cleanly against the old contract.

This is a contributing cause of the `confidence_tier` white-screen surviving
`tsc`: the frontend type and the backend model disagreed, and the mechanism that
should have caught it was reading its truth from a deployment rather than from
source. It also means frontend CI **cannot** detect a breaking API change until
the API is already live.

### N-6 — The frontend directory cannot tell you how it deploys

Eight deploy scripts coexist: `build-deploy.bat`, `build-deploy.ps1`,
`build-deploy2.ps1`, `build-deploy3.ps1`, `build-deploy4.ps1`,
`build-deploy5.bat`, `build_and_deploy.bat`, `deploy.bat`. Plus fourteen stale
`vite.config.ts.timestamp-*.mjs` files, a `dist-new/`, a `Claude outputs/`, a
`_to_delete/`, and `procs.txt` / `procs2.txt` / `npm-path.txt` /
`gsutil-path.txt`.

None of these is what CI uses. **The sprint began with a stale frontend build
live** — this is the environment that produces that, and it will produce it
again. Delete the lot; keep the CI workflow as the single path and say so in the
README.

## 4. Process — what actually went wrong

The sprint summary's own §5 is accurate and I am not going to restate it. Three
additions where I think the diagnosis can go one level deeper.

### P-1 — "The failure was dispatch, not decision" is right. Here is the mechanism.

DEC-A was recorded on 2026-08-31 as an accepted decision with an owner (O-2,
*"PROJECT-LEAD + Matt"*). Ten days later the capability did not exist. Nobody
dropped it through carelessness — **it was never on the board that dispatch reads
from.**

There are three live work boards in this repo:

| Board | Contains | Where dispatch actually happens |
|---|---|---|
| `PRE_SEASON_STATUS_2026-08-31.md` §4 | O-1 … O-13 | ❌ no |
| `DELEGATIONS.md` | six numbered tasks + carried debt | ✅ **yes** |
| `SPRINT-REVIEW-2026-09-10.md` §7 | open queue 1–7 | ❌ no |

An item can be open and owned on one and invisible on the other two. `DELEGATIONS.md`
is by some distance the best-run of the three — the ordering rationale, the "why 2
must precede 3" notes, and the honest reversal on DP-REVIEW's parallel-safety are
all genuinely good project management. The problem is not its quality; it is that
decisions are recorded somewhere else.

**Fix — one board.** `DELEGATIONS.md` becomes the only work board. Any decision
recorded in any document must either create a row on it, or carry the explicit
line *"no work follows from this decision."* A decision with an owner and no row
is the exact shape of the DEC-A failure, and it is detectable in one glance once
there is only one place to glance at.

### P-2 — "Code that has never met real data" is not a discipline problem

The sprint summary counts ten defects in three days of the same shape, and treats
it as a pattern to be noted. I would go further: **it is a missing environment,
and no amount of care will fix it.**

There is currently no place where code meets real data before production. There is
no staging dataset. No test runs against BigQuery. CI runs no tests at all. Every
path from *written* to *meets real data* runs through Matt's terminal or the live
service. Given that, ten defects of this shape is not a lapse — it is the
predicted output of the system.

The two fixes already applied are the right instincts and both are local:

- `preflight()` in `predict_upcoming.py` — checks all three target table schemas
  before ~90 seconds of loading. This is the pattern to institutionalise: **any
  code that writes to BigQuery reads the schema first.**
- `test_snapshot_lines.py` / `test_predict_upcoming.py` — assert against schema
  declarations in the repo, run with no credentials and no network. This is the
  right shape of test for this codebase and there should be more of them.

The general fix is §6 items 1 and 2: make the tests runnable without credentials,
then make CI run them. **91 tests have never gated a deploy.** Three dashboard
bugs shipped past a green pipeline during this sprint alone.

### P-3 — Make "deployed" checkable, now that it is

"Fixed" and "deployed" were repeatedly conflated in status reporting. That is now
a solvable problem rather than a discipline one, because `/health` reports a real
commit SHA for the first time in the repo's history.

**Institutionalise it:** a claim that something is deployed must cite the SHA that
`/health` returns. Make it a required field in every handoff document. It costs
one curl and it removes an entire category of ambiguity that cost a week during
INC-002.

### P-4 — Incident-mode boundary crossing should be explicit, not tolerated

PROJECT-LEAD edited five files in `01-DATA-PIPELINE` and one in `05-DEVOPS`
during INC-002. The board handles this well — DP-REVIEW and DO-HARDEN carry the
reviews, and DP-REVIEW found the edits were mostly correct and one file wrong,
which is exactly what the review was for.

Rather than forbidding it (which will be ignored under pressure) or leaving it
ad hoc, declare it: **during a live incident, role boundaries may be crossed, and
every crossing automatically generates a review task on the board before the
incident is closed.** That is what happened here by good judgement. Write it down
so it happens by default.

## 5. Things a reviewer should still be uneasy about

Not defects. Judgement calls worth revisiting deliberately.

**The confidence tiers mean nothing yet.** 0.10 / 0.05 were chosen to be
reasonable, not calibrated. Nobody has checked whether this model's 65% covers
65% of the time. Today the live slate has exactly one 'high' — at *p* = 0.341 —
and the word "high" is doing work on a dashboard that no measurement supports.
Either measure calibration (a platform capability, charter §5) or rename the
tiers to something that describes what they are: distance from a coin flip.

**`methodology.type` says `"walk_forward"` for what is forward prediction.**
Deliberate, documented in the source, test-asserted, and driven by a pydantic
`Literal` that would 500 the experiments list on the honest value. It is the
right call under the constraint. It is still a lie in a database that exists to
record what happened, and the constraint is a one-line enum change.

**`home_spread_close` means two different things depending on when it is read** —
a live value pre-game, the settled close afterwards. `predict_upcoming` stores the
prediction-time value, which is what makes closing-line value computable later.
The behaviour is right; the column name is wrong.

**The ungated serving path.** DEC-C permits it, the banner is driven by served
data rather than a local constant, and the override path is constrained so the
endpoint cannot be pointed at `test3-shuffle-labels-leakage-test` by query
string. I think this is the right trade and it is implemented carefully. A
reasonable reviewer could still hold that shipping unvalidated picks is wrong,
and that position should be recorded as considered rather than assumed away.

**No historical experiment can now be exactly reproduced.** Every backtest this
platform has ever run used `n_jobs=-1`. This does not overturn the finding that
no feature set cleared 54% — a ±0.04 hardware artifact cannot manufacture or hide
a real edge — but it should be written into `DECISIONS.md` as a bounded caveat on
the entire historical experiment log, not left in a sprint summary.

## 7. Closing assessment

**The platform crossed the line from "deployed" to "working" during this sprint.**
Before it, the app could not produce a prediction for a 2026 game, could not say
which code was running, had never actually shifted traffic through its own deploy
pipeline, and produced different numbers on different machines. All four are now
fixed and three of the four were verified rather than assumed.

The honest counterweight: the reason ten defects were available to find in three
days is that **the system has no way to catch them except by running in
production**. Every one of them was knowable from files already in the repo. The
work in §6 Tier 1 is not glamorous and it is the only thing that changes that.

And the framing question Matt raised is not a documentation problem. The OL
hypothesis keeps muddying the water because a gate the project retired in May is
still being written into the database every week and rendered to every visitor.
Fix the artifact and the framing stops drifting on its own.
